## 0. 方法论声明

三个镜头，由外到内：

1. **战略镜头（DDD 限界上下文）**：系统被切成了哪几个自治域，域间如何通信；
2. **本体镜头（Ontology 四视图）**：对象（是什么）、关系（怎么关联）、事件（发生了什么）、规则（什么永远成立）；
3. **基准镜头（成熟总账业务逻辑）**：三十年商业总账沉淀的领域概念与流程，我们覆盖了多少、偏差在哪。

复盘铁律：**所有结论必须落到代码事实**（类名/事件名/行为），不接受"设计文档上写了"。

## 1. 战略镜头：限界上下文地图

```
┌─────────────────────────────────────────────────────────┐
│                    Identity（身份上下文）                  │
│        Subject：人与 Agent 同表一等公民 + autonomy_level   │
└──────┬──────────────────────────────┬───────────────────┘
       │ actor 引用                    │ autonomy_level / quota
┌──────▼──────────┐   规则校验   ┌──────▼──────────────┐
│  Ledger Core    │◄────────────│  AuthZ（权限上下文）  │
│  （总账核心域）   │             │  Casbin RBAC×domain  │
│ Event/Voucher/  │             └─────────────────────┘
│ Account/Period  │◄────────────┐
└──────┬──────────┘             │
       │ POSTED 投影             │ 只读投影/事件
┌──────▼──────────┐   ┌─────────┴──────────┐   ┌──────────────────┐
│ Reporting       │   │ Integration（接入） │   │ Autonomy（自治）  │
│ 三表/对账/结转    │   │ Adapter/OCR/Bank   │──►│ 断路器/异常/L3    │
└─────────────────┘   └────────────────────┘   └──────────────────┘
       │                        │ 事件流
       └────────────┬───────────┘
              ┌─────▼──────┐
              │ Audit（审计）│ verify_chain / agent.decision / 回放
              └────────────┘
```

**评价**：
- ✅ 核心域（Ledger Core）与支撑域（AuthZ/Reporting/Integration/Autonomy）边界清晰，依赖方向正确（外围依赖核心，核心不依赖外围）——P2-01「零核心改动」的机器可验证断言就是这一原则的落地；
- ⚠️ **问题 1**：`Autonomy` 的断路器事件写死了 `ledger_set_id="__breaker__"` 哨兵值——断路器是**全局态**却寄生在账套维度的事件链上，语义错位。本体上「冻结」是 Subject 的属性演化，不是某账套的业务事件；
- ⚠️ **问题 2**：`Integration` 与 `Ledger Core` 之间没有防腐层（ACL）。适配器直接以内部约定（`记-` 前缀、`_accumulate_balances`）写核心模型——今天能跑是因为适配器就是我们自己写的；接第三方时这里会脆。

## 2. 本体镜头：四视图盘点

### 2.1 对象视图（是什么）

| 本体概念 | 实现 | 备注 |
|---|---|---|
| **聚合根** | `Voucher`（凭证） | 唯一的事务聚合，一致性边界内含明细行 |
| 实体 | `Subject` / `Account` / `Period` / `LedgerSet` / `PartnerObject`(aux) | |
| 值对象 | `Balance`（投影）、`dims_key`（canonical JSON）、`hash`（链式哈希） | Balance 注释明确「不是事实源」——本体定位准确 |
| **不变量（规则视图）** | 见 2.4 | |

### 2.2 关系视图（怎么关联）

```
LedgerSet 1─n Account（账套隔离，unique(ledger_set_id, code)）
LedgerSet 1─n Period  1─n Voucher 1─n VoucherLine
Account 1─n VoucherLine（aux_dims 挂 PartnerObject 维度，不建子科目）
Subject 1─n Voucher.created_by / Event.actor（人机同表）
Event 自引用链：prev_hash → hash（账套内成链）
```

**评价**：
- ✅ 「**往来明细不建子科目、用 aux_dims 承载**」是整个本体最正确的一条决策——与基准产品辅助核算思想同源，且避免了子科目爆炸；P2-02 之所以能在半天内挂上客户/供应商维度，就是因为当初留了这个缝；
- ⚠️ **问题 3**：`VoucherLine.aux_dims` 是自由 JSON，与 `Account.aux_dim_defs`（声明维度）之间的约束**只在适配器入口校验**，内核录入路径（`create_voucher`）不校验维度声明匹配——同一约束两处松紧不一；
- ⚠️ **问题 4**：`Balance` 投影按「借/贷发生额」累计，而 P1-02 结转后又做净零行清理、P1-04 对账改按净额比对——投影的本体语义经历了从「发生额」到「净额」的暗默转变，**契约漂移没有在模型注释里宣示**（今天已经咬过一口）。

### 2.3 事件视图（发生了什么）

实际落链的 20+ 事件类型按域归类：

| 域 | 事件 | 命名模式 |
|---|---|---|
| 凭证生命周期 | `voucher.created / pushed / approved / posted / cancelled` | ✅ 统一 `voucher.*` |
| 账务规则 | `opening_balance.imported` `closing.executed` | ⚠️ 前缀不一（`opening_` vs `closing_`） |
| Agent 治理 | `agent.decision` `agent.monthend.run` `agent.anomaly.detected` `agent.breaker.*` `agent.autonomous.*` | ✅ 统一 `agent.*` |
| 接入 | `adapter.event.consumed` `invoice.recorded` `ocr.invoice.flagged` `bank.txn.*` | ⚠️ 三种前缀混用 |

**评价**：
- ✅ 「**事件即事实源的动词过去式**」这一本体纪律执行得很好——今天两次靠回放事件流定位根因（额度统计断链、抽检追溯），就是回报；
- ⚠️ **问题 5**：事件命名无注册表。`agent.autonomous.posted` vs `agent.autonomous.reviewed` 的前缀错位（今天踩的额度恒 0 bug）本质是**字符串字面量没有单一事实来源**。建议：事件类型常量集中到 `kernel/events.py`，类 Enum 化，落链与查询都引用常量；
- ⚠️ **问题 6**：`invoice.received`（适配器规则事件名）与 `invoice.recorded`（OCR 管线查重事件）语义重叠——同一种业务事实有两个名字，通用语言（Ubiquitous Language）出现了方言。

### 2.4 规则视图（什么永远成立）

已固化为代码/测试的不变量：

| # | 不变量 | 固化位置 |
|---|---|---|
| 1 | 借贷必平衡（逐凭证） | `validate_voucher` + 逐笔断言 |
| 2 | 事件 append-only（哈希链） | SQLite/PG 触发器 |
| 3 | 制单 ≠ 审批；Agent 不能审批 | `state.transition` |
| 4 | 只允许 OPEN 期间记账 | `validate_voucher` |
| 5 | 试算不平衡拒绝期初 | `import_opening_balances` |
| 6 | 事件账本可由凭证明细全量重算 | `reconcile_ledger`（净额口径） |
| 7 | 未审凭证不得关账；Agent 不代审 | `monthend.run` 闸门 |
| 8 | 断路器只冻结 Agent | `check_breaker` |
| 9 | 自治过账需 L3+额度+断路器闭合 | `autonomous_post` |
| 10 | 抽检推翻=红字冲销，不删历史 | `audit_review` |
| 11 | 幂等：外部事件/流水/发票号只入账一次 | idempotency_key / 事件查重 |

**评价**：11 条不变量全部有测试背书——**规则视图是四个视图中最健康的一个**。

## 3. 基准镜头：成熟总账业务逻辑对照矩阵

> 内部对照口径：基准产品（代号 UB）指成熟商业总账模块的业务概念（凭证/账簿/期末/辅助核算），仅用于差距分析。

| 基准产品概念 | 基准产品（UB）业务逻辑要点 | XErp 现状 | 对齐度 | 差距/动作 |
|---|---|---|---|---|
| 凭证类别（记/收/付/转） | 类别字+断号管理，收付转分类 | 只有 `记-` 前缀 | 🟡 | 收/付/转类别是**查询优化与内控习惯**，非本体必需；P4 可做「凭证字」配置 |
| 制单→审核→记账 | 三步显式：审核（出纳/主管签字可选）→**记账**（显式动作过入账簿）→月末结账 | DRAFT→PUSHED→APPROVED→POSTED | 🟢 | 我们把「审核+记账」合并为状态机两跳，语义等价且更严格（防漏记） |
| 出纳签字 / 主管签字 | 现金凭证需出纳签字，可选主管签字 | 无二级签字 | 🔴 | **多级审批缺失**——状态机只有一层 APPROVED。建议：P4 做「签字位」抽象（Subject×角色×凭证的签署事件） |
| 作废与整理 | 凭证作废→整理断号 | `voucher.cancelled` 事件，无断号整理 | 🟢 | append-only 哲学下我们**更彻底**：不作废只冲销 |
| 红字冲销 | 红字凭证冲销错误账 | P3-03 抽检推翻已实现红字冲销 | 🟢 | 对齐 |
| **辅助核算** | 客户/供应商/部门/个人/项目 五维，科目档案声明启用 | aux_dims 四维（customer/supplier/department/project），科目声明 | 🟡 | 缺「个人往来」维度；且维度声明校验只在适配器（问题 3） |
| **期末转账** | 自定义转账/对应结转/损益结转/汇兑损益，模板化可配置 | 仅损益结转（声明式）+期初结转 | 🔴 | **最大差距**。UB 的转账模板是月结自动化的核心杠杆。建议 P4-01：把 `close_period` 的声明式规则引擎泛化为「转账模板」（公式化取数：科目×期间×方向×系数） |
| 对账 | 银行对账单勾对 + 未达账调节表 | P2-04 一对一勾对+双向报告 | 🟡 | 缺「余额调节表」产出物（勾对结果→法定格式报告）；一对多清分未做（已诚实留人工） |
| 账簿查询 | 总账/明细账/日记账/多栏账，可联查凭证 | `query_balances` 投影 + 单凭证详情 | 🔴 | **缺「明细账」**（按科目查逐笔流水并联查凭证）——这是会计日常最高频查询。数据都在（凭证明细+事件），只差查询接口。建议 P4 优先级最高 |
| UFO 报表关键字 | 年/月/账套三关键字取数 | 三表按期间投影 | 🟢 | 对齐，且我们有 A2UI 动态渲染（基准产品没有的能力） |
| 期初余额年初/月初 | 年初余额+科目年初余额表 | 期初凭证导入+期初结转 | 🟢 | 对齐且更简单 |
| 反记账/反结账 | 逆向操作（需主管权限） | `cancel_post_voucher`（ADR-004 窗口） | 🟡 | 有窗口控制但无「反结账后重开」完整回路——dogfood 10 月遇到错账时会被考到 |

**对照结论**：核心记账域（凭证/状态机/辅助核算/期末结转）**本体对齐度高且更严格**；差距集中在三处——**明细账查询**（高频缺口）、**转账模板**（月结杠杆）、**多级签字**（内控深度）。

## 4. 流程对照：状态机 vs 基准月结流程

基准：制单 → 审核 → （出纳/主管签字）→ 记账 → 月末转账 → 对账 → 结账
XErp：create → push → approve → post → **monthend_run（检查/催办/结转/试算/报表/开期）**

- ✅ 我们的月结是**编排好的原子流程**（P3-01），基准产品里是用户手工串的一串菜单——这是 Agent 原生的结构性优势；
- ✅ 关账闸门（未审中止+催办）对应基准的「结账前检查」且更强（不可绕过）；
- ⚠️ 缺「**反结账**」：发现上期错账需要「反结账→反记账→修改→重新结转」的完整回路，当前只有 cancel_post 窗口。这是 dogfood 真实使用前必须补的闭环（哪怕实现为「生成调整凭证」的红字路线，也要有明确 SOP）。

## 5. 复盘发现的债务清单（按痛排序）

| # | 债务 | 症状/证据 | 建议 |
|---|---|---|---|
| D1 | 事件类型字符串无注册表 | 额度恒 0 bug（前缀错位）；三种命名前缀混用 | 新建 `kernel/events.py` 常量注册表，全库替换（机械改动，半天） |
| D2 | 明细账查询缺失 | 会计最高频操作不可用 | P4 首项：`ledger_detail(account_code, period)` 联查凭证明细 |
| D3 | 转账模板缺失 | 月结自动化只覆盖损益结转 | 泛化 close_period 规则引擎为模板化转账 |
| D4 | 断路器哨兵账套 `__breaker__` | 全局态寄生账套事件链 | 迁移到 Subject 级事件或独立状态表 |
| D5 | aux_dims 校验双标 | 适配器严、内核松 | 把维度声明校验下沉到 `validate_voucher` |
| D6 | 投影语义契约漂移 | 净额 vs 发生额已咬人一次 | Balance 文档宣示「净额口径」+ 测试固定 |
| D7 | 多级签字缺失 | 内控深度不足（对一人公司无感，对多角色客户是硬需求） | P4「签字位」设计 |
| D8 | Integration 无 ACL | 适配器直连内部符号 | 保持零核心改动断言即可，暂不动 |

## 6. 一句话总结

> **本体骨架（事件账本 + 凭证聚合 + aux_dims 辅助核算 + 声明式规则）经基准对照后依然站得住，且在人机协同（自治/断路器/抽检）上走在了基准产品前面；主要债务不在架构而在「通用语言的纪律」——事件命名注册表、投影契约宣示、维度校验归一，这三件事是把隐性知识显性化，工作量小、收益立竿见影。**
