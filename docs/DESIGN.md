# XErp — 智能体 ERP 整体设计与可行性分析

> 版本 v0.1 草案 · 2026-08-27 · 丞辰 × 小煖  
> 定位：AI Native 自运行组织的开源财务/业务内核，从总账（GL）单点纵深切入  
> 证据基础：成熟商业总账产品的治理机制分析+ A2UI 协议（Google v0.9）+ Palantir Ontology 参照



---

## 0. 结论先行

**可行性判定：可行，但有三个先决条件。**

| #  | 判定           | 依据                                                                           |
| -- | ------------ | ---------------------------------------------------------------------------- |
| 技术 | ✅ 可行         | A2UI 协议已标准化（Apache 2.0）、MCP 生态成熟、PostgreSQL 足以承载 Ontology+账本；无人值守所需的全部原语均已存在 |
| 业务 | ✅ 可行（限于总账切入） | 复式记账是 500 年不变的确定性规则，天然适合「确定性内核 + 概率性外壳」；总账是 ERP 中规则最清晰、数据量最小、价值最高的单点         |
| 合规 | ⚠️ 有条件       | 财务数据不可篡改与审计留痕是硬约束；无人值守必须有分级门控；**绝不可反编译/复用成熟商业总账厂商代码与模板（clean-room）**               |

三个先决条件：

1. **确定性内核**：LLM 永不手写分录金额，借贷平衡等不变量由引擎强制，AI 只做理解、编排、解释；
2. **审计即架构**：append-only 事件溯源从第一行代码就是地基，不能后补；
3. **单点纵深**：P0-P2 咬死总账，拒绝范围蔓延——这是对「传统 ERP 实施难」最直接的反叛：不是再造 90 个 MSI，而是让 90 个模块的公共分母（凭证）先跑起来。

## 1. 问题定义：传统 ERP 的「三难」病灶

我们逆向过 传统总账产品 V18.0 完整介质（4.1GB、90 个 MSI、2070 个文件仅总账一个模块），病灶有一手证据：

| 病灶      | 一手证据                                                    | Agent ERP 的反叛                                        |
| ------- | ------------------------------------------------------- | ---------------------------------------------------- |
| **实施难** | InstallShield 引导 + 90 MSI 依赖拓扑 + .NET/VC++/SQLCLR 前置依赖链 | `docker compose up` + 对话式 Drill 初始化（建账套→科目表→期初），打开即用 |
| **维护难** | CustomAction 文件日期比对 + UFBAK 备份回滚的增量补丁机制，补丁间强耦合          | GitOps 声明式升级 + 事件溯源天然可回放                             |
| **上手难** | 仅总账就有 1968 个 .rep 打印模板、三代冗余并存的科目组件                      | A2UI 按需生成界面，模板目录只保留必要兜底；对话即操作                        |

深层洞察：**传统 ERP 的复杂度大半来自「为每种人预先画好每种界面」**。Agent ERP 把界面生成推迟到交互时刻（A2UI），把业务规则收敛为本体（Ontology），把流程编排交给 AI Runtime——复杂度从百万行代码转移到模型的理解力，而模型的理解力是随时间免费升级的。

## 2. 核心资产：传统总账逻辑 → Agent 原语映射表

这是我们区别于所有「ChatGPT 套壳 ERP」的实证基础。传统总账用三十年验证的治理机制，逐一对应：

| 传统总账机制（实证）                       | 本质      | XErp 对应物                                                          |
| --------------------------------- | ------- | --------------------------------------------------------------------- |
| 总账 = 凭证汇聚总线（18 个模块经固定 DLL 接口汇入凭证） | 事件汇聚    | **业务事实 → 领域事件 → 账务化 Pipeline**，新模块接入=发布一个事件适配器，而非改造核心                 |
| 凭证状态机：填制→审核→记账→结账 + 逆向取消          | 有界自治    | **HITL 状态机：Draft → Push → Review → Commit → Closed**，与你手稿完全同构；逆向=补偿事务 |
| BPM-BM 预算控制 17 组件，凭证保存时生效         | 护栏      | **Policy as Code**：预算/合规规则在 Action 执行前强制校验，AI 绕不过                     |
| code 科目表 + 辅助核算                   | 语义骨架    | **Ontology**：Account/Voucher/Period 对象 + 属性 + 关系（Palantir 同构）         |
| 凭证表/汇总表           | 事实与汇总分离 | **Event Sourcing**：分录事件 append-only，余额=物化投影，天然可回放可审计                  |
| USKMSET/USKMREF/KmRefTbl 三代冗余并存   | 演进包袱    | **单一 Ontology Schema + 版本迁移**，杜绝并存                                    |
| 1968 个 .rep 打印模板                  | 静态 UI   | **A2UI 蓝图 + 模板目录兜底**：凭证卡片/三表/明细账由 Agent 动态生成，复杂格式用预置模板                |
| 总账组件.DLL 统一数据通道                  | 受控访问    | **MCP Resource 网关**：Agent 只能经权限内检索接口读数，不直连 DB                         |
| 共享组件层 共享组件库                    | 能力复用    | **MCP Server 工具集**（create_voucher / post / close_period…）             |
| 传统总账对外接口           | 集成面     | **对外 MCP + A2A endpoint**，天然可被 WorkBuddy/飞书 Bot 消费                    |
| KMZHTOOL 科目转换工具                   | 迁移      | **Drill 初始化向导**：对话式导入旧科目表+期初余额（CSV/截图/口述）                             |

> 合规红线：以上映射仅借鉴**业务逻辑概念**（复式记账、状态机、汇聚模式均为行业公有知识），开源实现全部 clean-room，不接触成熟商业总账厂商二进制。

## 3. 总体架构（对应手稿八要素）

```
┌─ L7 部署交付 ── docker compose / 单二进制 / WorkBuddy Skill 一键装
├─ L6 应用层 ──── 飞书 Agent · 微信 · Web · Pi（同一 MCP 后端）
├─ L5 前端 A2UI ─ Google A2UI v0.9 渲染器（React/飞书小程序适配）+ 模板目录
├─ L4 编排 ────── Dify（可视化编排）｜自研 Planner（默认）｜可插拔
├─ L3 AI Runtime  会话·任务·定时·HITL(Push→Review→Commit)·护栏·断路器
├─ L2 能力层 ───── MCP Server: Tools(记账/过账/关账) + Skills(准则知识) + Resources(查询)
├─ L1 Ontology ── 对象/属性/关系 + Policy as Code + Event Ledger(append-only)
└─ L0 审计与权限  身份 · 数据权限(账套/科目) · 功能权限 · 全量决策留痕
```

**五条铁律**：

1. **确定性内核 + 概率性外壳**：金额计算、借贷平衡、期末结转全部由确定性引擎执行；LLM 负责把自然语言→结构化意图、把数据→解释。每张 AI 起草的凭证都带「证据链」（来源单据/推理摘要）。
2. **一切皆事件**：过账是事件，审批是事件，AI 的每次工具调用也是事件——审计 = 回放事件流。
3. **权限先于功能**：数据权限（哪账套/科目可见）、功能权限（谁可授权 AI 做什么）、自治额度（Agent 每月可免审金额上限）三维度，继承 传统总账 三层权限模型并增加「Agent 身份」为一等公民。
4. **HITL 分级自治**：L0 只读问答（免审）→ L1 草拟单据（人审 Commit）→ L2 例行任务（例外审批）→ L3 预算内自主+抽检。升级/降级由风险策略驱动，默认最低档。
5. **失败安全**：断路器 + 回放。任何异常冻结自治、降级到人。

## 4. 总账内核设计（P0 范围）

### 4.1 Ontology 最小模型

```
Account(科目): code, name, direction(借/贷), aux_dims[部门/往来/项目]
Voucher(凭证): no, date, period, lines[] {account, debit, credit, aux, summary}
Period(期间):   status[Open/Closing/Closed], carry_forward_rules[]
Balance(余额):  period × account × dims → 物化投影(可重建)
Party/维度对象: 客户、供应商、部门、项目（辅助核算本体）
```

### 4.2 状态机（继承传统总账并 Agent 化）

```
Draft ──Push──► InReview ──Approve──► Posted ──期末──► Closed
  ▲                │驳回                  │取消记账(未结账)
  └────── 补偿事务 ─┴─────────────────────┘
```

- `Push`：AI 或人提交，自动触发 Policy 校验（预算/余额方向/凭证字合规）
- `Review`：A2UI 渲染凭证卡片，审批人一键通过/驳回，驳回意见回写事件流
- `Commit`：确定性引擎过账（借贷不平衡在此被硬拒），写 Event Ledger
- `Closed`：结转规则（损益结转等）以声明式配置存于 Period，由关账 Agent 执行

### 4.3 三表即投影

资产负债表/利润表/现金流量表 = Event Ledger 上的物化视图 + 科目映射配置（内置小企业会计准则与一般企业准则模板）。现金流量表需现金流量项目辅助核算标注，P1 支持。

### 4.4 Drill 初始化（打开即用的关键）

首次启动 → 对话向导：行业→准则→科目表（模板或导入）→ 期初余额（支持拍照/CSV/口述录入，AI 结构化+试算平衡）→ 5 分钟出第一张凭证。这是「脱离实施」的承诺兑现点。

## 5. 技术选型

| 层    | 选型                                                 | 理由                                           |
| ---- | -------------------------------------------------- | -------------------------------------------- |
| 内核   | Python(FastAPI) 或 Go + PostgreSQL(JSONB)           | 账本用关系型约束保不变量；JSONB 承载 Ontology 灵活属性；单机可跑=易交付 |
| 事件账本 | PG append-only 表 + hash 链（类 blockchain-lite 防篡改校验） | 审计可验证，无重运维                                   |
| 能力层  | MCP（Python SDK）+ SKILL.md 打包                       | 与 WorkBuddy/主流 Agent 客户端零适配成本                |
| 前端   | A2UI 官方 React 渲染器 + 飞书消息卡片映射                       | 标准协议不自造；飞书卡片=移动端 A2UI 渲染器                    |
| 编排   | 自研轻 Planner 为默认；Dify 作为可视化编排可选后端                   | 避免重依赖；保留低代码人群入口                              |
| LLM  | DeepSeek（本地 DSH）/ 任意 OpenAI 兼容端点，可插拔               | 成本与私有化友好                                     |
| 权限审计 | Casbin 风格策略 + 全量事件留痕（prompt/工具调用/输出摘要）             | 满足内外审                                        |

## 6. 可行性分析（风险×对策）

| 维度       | 风险               | 等级 | 对策                                              |
| -------- | ---------------- | -- | ----------------------------------------------- |
| 记账幻觉     | AI 算错金额/科目       | 高  | 确定性内核硬不变量；AI 仅起草；金额类字段必须来自工具返回而非模型生成            |
| 合规审计     | 电子凭证法律效力、留痕不满足审计 | 高  | append-only+hash 链+时间戳；早期请会计专业朋友评审；对标电子会计档案规范   |
| A2UI 成熟度 | v0.9 仍在演进        | 中  | 协议已可生产使用；模板目录兜底核心界面（凭证卡片/三表）                    |
| 无人值守失控   | 自治操作越界           | 高  | 分级自治+预算额度+断路器+全量回放；L3 默认关闭                      |
| 范围蔓延     | 总账没做完就做全模块       | 高  | 铁律：P0-P2 只做总账；模块以事件适配器渐进接入                      |
| 法律隔离     | 被质疑借鉴成熟商业总账厂商代码        | 中  | clean-room：不反编译、不复制模板；文档留痕我们只参考了 MSI 元数据与公有会计知识 |
| 生态冷启动    | 开源无人用            | 中  | 吃自己狗粮（我们自己的公司账套）+ WorkBuddy/飞书技能包分发 + 公众号内容营销   |

**工程量粗估**（一人 + AI 结对）：P0 约 3-4 周；P1 约 6-8 周；P2 约 8 周。相比传统 ERP 团队年级投入，数量级优势来自：不做 UI（A2UI 生成）、不做流程引擎（AI Runtime 即流程）、不做实施（Drill 初始化）。

## 8. 开源与易交付策略

- **License**：Apache-2.0（生态最友好）；若未来担忧云厂商白嫖，核心账本引擎可单独 AGPL（双层策略，初期不必）
- **一键交付**：`docker compose up` → 浏览器打开 → Drill 对话初始化；进阶单二进制 + SQLite（个人/演示）
